# Окружение: Docker, psql и что происходит при подключении

> [!abstract] Реляционная модель и окружение · урок 1 из 4
> Поднимаем PostgreSQL 18 в Docker, осваиваем psql и разбираем, почему одно соединение — это целый процесс ОС и зачем нужен пул.

## Где мы

Это первый урок учебника, поэтому коротко о том, куда мы идём. Ты умеешь писать `SELECT` с `JOIN` и `GROUP BY` и работал с базой через EF Core. Этого хватает, чтобы данные из базы доставать. Этого не хватает, чтобы понимать, почему запрос медленный, почему два пользователя затёрли друг другу данные и почему `ALTER TABLE` положил прод на минуту.

Сквозная мысль всей книги: SQL описывает результат, а Postgres сам решает, как его получить. Почти каждая проблема с базой — это разрыв между тем, что ты написал, и тем, что база сделала. Чтобы этот разрыв видеть, нужно знать, что база делает. Этим и займёмся.

Глава 1 — подготовительная. В ней мы ставим окружение, разбираемся, что такое таблица и ключ по-взрослому, выбираем типы данных и учимся защищать данные ограничениями. Этот урок — про окружение и про первое, что Postgres делает, когда ты к нему подключаешься.

## Что такое Postgres как программа

Начнём с бытового. PostgreSQL — это серверная программа. Она запускается один раз, слушает сетевой порт (по умолчанию 5432) и ждёт, когда к ней кто-нибудь подключится. Подключиться может что угодно: твой терминал, веб-приложение на ASP.NET Core, агент практики, инструмент вроде DBeaver. Все они общаются с сервером по одному и тому же протоколу: присылают текст запроса, получают назад строки.

Внутри сервера данные лежат в файлах на диске. Postgres сам решает, когда читать с диска, а когда взять из памяти, когда писать и в каком порядке. Клиент об этом не знает и знать не должен.

Из этого простого описания вытекает первая неочевидная вещь, и она станет центральной в этом уроке: подключение к Postgres — это не «открыть сокет». Это гораздо дороже. Но сначала поставим сервер и посмотрим на него.

## Поднимаем сервер в Docker

Нам нужен PostgreSQL 18. Ставить его на машину напрямую не будем: Docker даёт изолированный сервер, который можно снести и поднять заново за минуту.

```bash
docker run -d --name pg18 \
  -e POSTGRES_PASSWORD=postgres \
  -p 5432:5432 \
  postgres:18
```

**Что происходит.** Docker скачивает образ `postgres:18` и запускает контейнер с именем `pg18`. Внутри контейнера стартует сервер Postgres. Переменная `POSTGRES_PASSWORD` задаёт пароль суперпользователя `postgres`. Флаг `-p 5432:5432` пробрасывает порт контейнера наружу, чтобы к серверу можно было подключиться с твоей машины как к `localhost:5432`.

Проверим, что сервер жив:

```bash
docker exec -it pg18 psql -U postgres -c 'SELECT version();'
```

**Что происходит.** `docker exec` запускает команду внутри контейнера. Команда — `psql`, консольный клиент Postgres. Флаг `-U postgres` задаёт пользователя, `-c` передаёт один запрос и выходит. В ответ придёт строка вида `PostgreSQL 18.x on x86_64-pc-linux-gnu ...`.

## Загружаем учебную базу

Учебная база называется `freight`. Это грузоперевозки по Европе: клиенты заказывают перевозки, диспетчеры назначают водителей и грузовики, грузовики шлют GPS-события, по доставленным грузам выставляются счета. Все примеры в учебнике — на ней. Схему разберём в [[1.2-Реляционная модель на примере freight|следующем уроке]], сейчас просто загрузим.

```bash
docker exec -it pg18 psql -U postgres -c 'CREATE DATABASE freight'
docker cp sql-03-uchebnaya-baza.sql pg18:/tmp/
docker exec -it pg18 psql -U postgres -d freight -f /tmp/sql-03-uchebnaya-baza.sql
```

**Что происходит.** Первая команда создаёт пустую базу данных `freight`. Внутри одного сервера Postgres может быть много баз, и они друг друга не видят. Вторая команда копирует скрипт внутрь контейнера. Третья выполняет скрипт в базе `freight`: флаг `-d` выбирает базу, `-f` читает команды из файла. Скрипт создаёт схему `freight`, одиннадцать таблиц и генерирует около 3.5 миллионов строк. Занимает это от 20 секунд до пары минут. В конце скрипт выводит две контрольные таблички: количество строк по таблицам и несколько проверок.

Одна деталь сразу пригодится. В первой контрольной табличке строки выводятся не в том порядке, в каком перечислены в запросе: `dispatchers` может оказаться раньше `cities`. Запрос там собран из `UNION ALL` без `ORDER BY`, а без `ORDER BY` Postgres порядок строк не обещает. Никогда. Это не баг, это правило, и мы вернёмся к нему в уроке 2.3.

## psql: команды, без которых не обойтись

psql — это консольный клиент, и в этой книге он основной инструмент. Не потому, что графические клиенты плохие, а потому, что в psql видно ровно то, что делает база, без прослойки интерфейса. На собеседовании тоже чаще дадут консоль или окно с голым SQL.

Подключаемся к базе интерактивно:

```bash
docker exec -it pg18 psql -U postgres -d freight
```

Теперь мы внутри psql. Здесь два типа команд. Обычный SQL заканчивается точкой с запятой и уходит на сервер. Команды, начинающиеся с обратного слэша, — это команды самого psql: они выполняются на клиенте и помогают осмотреться.

|Команда|Что делает|Когда нужна|
|---|---|---|
|`\l`|список баз данных на сервере|убедиться, что `freight` создана|
|`\c freight`|переключиться на базу|если зашёл не туда|
|`\dn`|список схем в базе|увидеть схему `freight`|
|`\dt freight.*`|список таблиц в схеме|осмотреться в базе|
|`\d freight.shipments`|структура таблицы: колонки, типы, ограничения, индексы|первое, что делаешь с незнакомой таблицей|
|`\d+ freight.shipments`|то же плюс размер и комментарии|когда нужен размер или описание|
|`\x`|переключить расширенный вывод: каждая строка — столбиком|когда колонок много и строка не влезает в экран|
|`\timing`|показывать время выполнения каждого запроса|всегда, когда говорим о производительности|
|`\e`|открыть последний запрос в редакторе|править длинный запрос|
|`\i file.sql`|выполнить команды из файла|загрузить скрипт изнутри psql|
|`\?`|справка по командам psql|забыл команду|
|`\h ALTER TABLE`|справка по синтаксису SQL-команды|забыл синтаксис|
|`\q`|выйти||

Попробуй прямо сейчас:

```sql
\dt freight.*
\d freight.shipments
```

**Что происходит.** Первая команда показывает одиннадцать таблиц схемы `freight`. Вторая показывает колонки таблицы `shipments` с типами, какие колонки могут быть `NULL`, какие значения по умолчанию, а ниже — ограничения, индексы и внешние ключи. Это описание таблицы, которое psql собирает из системного каталога — служебных таблиц, где Postgres хранит информацию обо всех объектах базы. В [[1.2-Реляционная модель на примере freight|следующем уроке]] мы будем читать такие описания как карту.

## Схема и search_path

Ты заметил, что везде пишется `freight.shipments`, а не просто `shipments`. Таблицы живут в схеме `freight`, а по умолчанию Postgres ищет таблицы в схеме `public`. Писать префикс каждый раз утомительно. Есть параметр `search_path` — список схем, в которых Postgres ищет таблицу, если имя дано без префикса.

Можно настроить его на время сессии:

```sql
SET search_path TO freight, public;
```

Но тогда придётся повторять это при каждом входе. Лучше один раз привязать к базе:

```sql
ALTER DATABASE freight SET search_path TO freight, public;
```

**Что происходит.** Параметр сохраняется в настройках базы и применяется к каждому новому соединению с ней. Текущая сессия его не подхватит, нужно переподключиться (`\q` и войти заново). После этого `SELECT count(*) FROM shipments;` работает без префикса. Все запросы в учебнике дальше написаны в расчёте на это.

Проверим, что всё работает, и заодно включим таймер:

```sql
\timing
SELECT count(*) FROM shipments;
```

**Что происходит.** Postgres читает таблицу `shipments` целиком и считает строки. Должно получиться 300000. Под результатом psql покажет время: на 300 тысячах строк это десятки миллисекунд. Запомни порядок величины, с ним будем сравнивать.

## Что произошло, когда ты подключился

Теперь главное в этом уроке. Ты набрал `psql` и оказался в консоли. Выглядит мгновенно. Посмотрим, что сделал сервер.

В Postgres есть главный процесс. Исторически он называется postmaster, и это слово до сих пор встречается в документации и логах. Он запускается первым, слушает порт 5432 и сам запросы не выполняет. Его работа — принимать подключения.

Когда приходит новое подключение, postmaster делает `fork()`: создаёт копию себя как отдельный процесс операционной системы. Этот новый процесс называется backend. Он обслуживает ровно одно соединение, ровно одного клиента, и живёт, пока клиент не отключится. Ещё одно подключение — ещё один fork, ещё один backend. Сто подключений — сто процессов.

![[1.1-postmaster-backends.png]]
*Рис. 1.1.1. Одно соединение = один процесс ОС. Клиенты ходят не «в базу», а каждый в свой backend.*

Убедимся сами. Прямо из своей сессии psql спроси, какой процесс тебя обслуживает:

```sql
SELECT pg_backend_pid();
```

**Что происходит.** Функция возвращает идентификатор процесса операционной системы (PID), который выполняет твои запросы. Это и есть твой backend. Число будет вроде 87 или 412.

Теперь посмотрим на все процессы Postgres снаружи, из другого терминала:

```bash
docker top pg18
```

**Что происходит.** Docker показывает процессы внутри контейнера. Среди них будет главный процесс `postgres` и несколько служебных: `checkpointer`, `background writer`, `walwriter`, `autovacuum launcher` и другие. Что они делают — тема глав 11 и 13, пока просто отметь, что сервер — это не один процесс, а семья. И среди них будет строка вида:

```text
postgres: postgres freight [local] idle
```

Это твой backend. Postgres подписывает процессы: пользователь, база, откуда подключение и что сейчас делает. `idle` значит «ждёт следующего запроса». Открой второе окно psql и запусти `docker top` снова — появится второй такой процесс. Закрой окно — исчезнет.

То же самое видно изнутри базы, через системное представление `pg_stat_activity`:

```sql
SELECT pid, usename, datname, application_name, state, backend_type
FROM pg_stat_activity
ORDER BY backend_type, pid;
```

**Что происходит.** `pg_stat_activity` — это окно в список всех процессов сервера. Колонка `backend_type` отличает клиентские backend-ы (`client backend`) от служебных процессов. Колонка `state` показывает, занят процесс запросом или простаивает. Своё соединение узнаешь по `pid`, который вернул `pg_backend_pid()`. К этому представлению мы будем возвращаться постоянно: в главе 12 именно здесь будем искать, кто кого заблокировал.

## Почему соединение дорогое

Итак, одно подключение — один процесс. Разберём, что стоит за секундой между нажатием Enter и приглашением psql.

![[1.1-connection-stages.png]]
*Рис. 1.1.2. Четыре этапа из шести — накладные расходы, и они повторяются при каждом новом подключении.*

Первый этап — сеть. TCP-рукопожатие, а в проде ещё и TLS. Это обмен несколькими пакетами туда-обратно.

Второй — `fork()`. Операционная система создаёт новый процесс: выделяет ему память, копирует служебные структуры, ставит в планировщик. Это сотни микросекунд в лучшем случае, и это самая дорогая часть на стороне сервера.

Третий — аутентификация. Postgres смотрит в файл `pg_hba.conf`, решает, каким способом проверять этого клиента, обменивается с ним паролем или сертификатом.

Четвёртый — прогрев. Новый backend ничего не знает о базе. Он должен загрузить в свою память сведения о таблицах, типах, функциях, правах — всё из системного каталога. Это кэши, частные для каждого процесса, и они заполняются по мере первых запросов. Поэтому первый запрос в свежем соединении медленнее, чем тот же запрос через секунду.

Только после этого начинается пятый этап — полезная работа. А шестой, завершение соединения, убивает процесс вместе со всеми его прогретыми кэшами.

Теперь сравни. Простой `SELECT` по первичному ключу выполняется за доли миллисекунды. Установка соединения — миллисекунды, часто десятки. Если приложение на каждый HTTP-запрос открывает соединение, делает один `SELECT` и закрывает, то на сам запрос уходит один процент времени, а на обслуживание соединения — девяносто девять.

Это одна сторона проблемы. Вторая — количество. Каждый backend занимает память: несколько мегабайт базово, плюс всё, что он выделяет под сортировки и хэш-таблицы при выполнении запросов. Тысяча соединений — тысяча процессов, которые делят между собой процессорные ядра и соревнуются за общие структуры в памяти. Postgres ограничивает их число параметром `max_connections` (по умолчанию 100, **VERIFY**), и это ограничение существует не из вредности.

## Пул соединений

Решение очевидно, когда проблема понятна: не открывать соединение на каждый запрос, а открыть заранее несколько и переиспользовать.

![[1.1-connection-pool.png]]
*Рис. 1.1.3. Соединений мало, запросов много; пул выдаёт соединение на время запроса и забирает назад.*

Пул живёт на стороне приложения. При старте он открывает несколько соединений (или открывает по мере надобности, но не закрывает после использования). Когда коду нужна база, он берёт свободное соединение из пула, выполняет запрос и возвращает соединение назад. Постгресовский backend при этом не умирает: он сидит в состоянии `idle` и ждёт следующего владельца. Все его кэши прогреты.

Когда соединений не хватает на всех, запросы в приложении ждут в очереди. Это правильно: сто запросов, выстроившихся в очередь к двадцати соединениям, работают быстрее, чем сто соединений, дерущихся за восемь ядер.

Пул бывает двух видов. Пул внутри приложения (в .NET это Npgsql) — для одного приложения. Внешний пул (PgBouncer) — когда приложений много, или их много экземпляров, и суммарно они хотят больше соединений, чем Postgres может переварить. Про PgBouncer и его ограничения поговорим в главе 13. Пока главное — зачем он нужен.

> [!example] Мост в .NET
> Npgsql включает пул по умолчанию: в строке подключения `Pooling=true`, если не сказано иное. Когда ты пишешь `await using var conn = new NpgsqlConnection(cs); await conn.OpenAsync();`, физическое соединение не открывается, а берётся из пула. `Dispose` его не закрывает, а возвращает в пул. Размер пула задаётся параметрами строки подключения `MinPoolSize` и `MaxPoolSize` (по умолчанию 0 и 100, **VERIFY**). EF Core создаёт `DbContext` на каждый HTTP-запрос, и это нормально: `DbContext` дешёвый, а соединение под ним он берёт из того же пула Npgsql. Если ты видел в логах ошибку про исчерпанный пул (`The connection pool has been exhausted`, **VERIFY** точный текст), это означает, что все `MaxPoolSize` соединений заняты и кто-то их не возвращает — обычно незакрытая транзакция или забытый `Dispose`.

## Где ломается

**Соединение на запрос.** Код, который открывает `NpgsqlConnection` без пула, или скрипт, который вызывает `psql -c` в цикле на каждую строку, тратит основное время на установку соединений. Симптом: база почти не нагружена, а всё медленно.

**Много idle-соединений.** Двадцать экземпляров приложения с `MaxPoolSize=100` — это потенциально две тысячи соединений к одному Postgres, из которых большая часть простаивает. Каждое ест память и место в `max_connections`. Когда лимит кончается, новое подключение получает ошибку `too many clients already` (**VERIFY** точный текст), и это ошибка не того, кто подключается последним, а архитектуры. Решение: уменьшить пулы или поставить PgBouncer.

**Состояние сессии живёт в backend-е.** `SET search_path`, временные таблицы, prepared statements — всё это принадлежит процессу, а не базе. Если ты сделал `SET` в одном соединении из пула, оно сохранится в этом соединении и достанется следующему, кто его возьмёт. Npgsql при возврате в пул сбрасывает состояние (**VERIFY**: по умолчанию посылает `DISCARD ALL`, отключается параметром `No Reset On Close`), но внешние пулы в некоторых режимах этого не делают. Отсюда баги вида «иногда запрос работает в другой схеме». Подробности в главе 13.

## Глубже / на синьора

**Почему процессы, а не потоки.** Большинство современных СУБД (MySQL, SQL Server, Oracle в части режимов) обслуживают соединения потоками внутри одного процесса. Postgres исторически выбрал процессы: в 1990-х это было надёжнее — упавший backend не утащит за собой весь сервер, у каждого процесса своё адресное пространство. Цена: fork дороже создания потока, а общие данные надо явно класть в разделяемую память (shared memory), а не просто в глобальную переменную. В сообществе давно обсуждается переход на потоки, работа в этом направлении идёт (**VERIFY** статус на момент PostgreSQL 18), но в текущих версиях модель процессная.

**Два вида памяти.** У каждого backend-а есть своя приватная память: туда идут кэши каталога, рабочая память под сортировки (`work_mem`), временные буферы. И есть общая для всех процессов память: shared buffers (кэш страниц с диска), таблица блокировок, буферы журнала WAL. Через общую память backend-ы и видят одни и те же данные. Это разделение объясняет, почему `work_mem` — параметр на операцию, а `shared_buffers` — один на сервер. Вернёмся к этому в главе 8.

**Idle не бесплатен.** Даже простаивающее соединение стоит не только памяти. При каждом новом снапшоте (а в Read Committed это каждый оператор) Postgres просматривает список всех активных процессов, чтобы понять, какие транзакции сейчас идут. Чем больше процессов, тем дороже каждый снапшот. В PostgreSQL 14 это место сильно оптимизировали (**VERIFY**), но закон остался: тысяча соединений замедляет всех, даже если девятьсот из них ничего не делают.

**Почему нельзя просто поднять `max_connections`.** Можно, и Postgres послушается. Но каждое соединение резервирует место в общих структурах, а реально работать параллельно могут столько запросов, сколько есть ядер и дисковой пропускной способности. Правило большого пальца от команд, которые занимаются Postgres профессионально: оптимальное число активных соединений — порядка числа ядер, умноженного на небольшой коэффициент (**VERIFY**: часто цитируется формула `cores * 2 + effective_spindle_count` из вики PostgreSQL). Всё сверх этого — очередь, и лучше ей стоять в пуле, чем внутри базы.

## Насколько важно для собесов

- Процессная модель, один backend на соединение — 🟡 часто на Middle+, почти всегда в вопросе «почему нужен пул».
- Почему соединение дорогое — 🔴 спрашивают почти всегда, обычно через пул или через N+1.
- Пул Npgsql, `MaxPoolSize`, исчерпание пула — 🔴 для .NET-позиций.
- psql и его команды — ⚪ не спрашивают, но на live-coding выручает.
- PgBouncer и внешние пулы — 🟡, подробно в главе 13.

## На собесе

> [!question]- Почему соединение с PostgreSQL считается дорогим?
> **RU:** Postgres создаёт отдельный процесс операционной системы на каждое соединение. Установка включает TCP и TLS-рукопожатие, fork процесса, аутентификацию и прогрев кэшей каталога в новом процессе. Это миллисекунды, тогда как простой запрос выполняется за доли миллисекунды. Плюс каждый процесс занимает память и место в `max_connections`. Поэтому соединения не открывают на каждый запрос, а держат в пуле.
>
> **EN:** Postgres spawns a separate OS process for every connection. Establishing one means a TCP and TLS handshake, a process fork, authentication, and warming up the catalog caches in the new process. That takes milliseconds, while a simple query takes a fraction of a millisecond. Each process also consumes memory and a slot in `max_connections`. That’s why connections are pooled rather than opened per request.

> [!question]- Что такое connection pool и зачем он нужен?
> **RU:** Пул — это набор заранее открытых соединений на стороне приложения. Код берёт соединение на время запроса и возвращает назад, физическое соединение не закрывается. Это убирает стоимость установки соединения и ограничивает их число сверху. В .NET пул встроен в Npgsql и включён по умолчанию, размер задаётся `MaxPoolSize`. Если соединений не хватает, запросы ждут в очереди, что лучше, чем перегрузить базу.
>
> **EN:** A pool is a set of pre-opened connections kept on the application side. Code borrows a connection for the duration of a request and returns it; the physical connection stays open. This removes connection setup cost and caps the total number of connections. In .NET the pool is built into Npgsql and enabled by default, sized by `MaxPoolSize`. When no connection is free, requests queue, which beats overloading the database.

> [!question]- Чем отличается пул в приложении от PgBouncer?
> **RU:** Пул в приложении, например в Npgsql, работает внутри одного процесса приложения. Если экземпляров приложения двадцать, у каждого свой пул, и суммарно соединений может быть больше, чем база выдерживает. PgBouncer стоит между всеми приложениями и базой и держит общий небольшой набор серверных соединений. Цена — ограничения на состояние сессии в некоторых режимах, об этом надо помнить при настройке.
>
> **EN:** An in-app pool like Npgsql’s lives inside one application process. With twenty app instances you get twenty pools, and the total can exceed what the database handles. PgBouncer sits between all applications and the database and maintains one shared, small set of server connections. The cost is restrictions on session state in some modes, which you need to account for when configuring it.

> [!question]- Что делать, если приложение получает ошибку исчерпания пула?
> **RU:** Сначала найти, кто не возвращает соединения: обычно это незакрытые транзакции, долгие запросы или пропущенный `Dispose`. В `pg_stat_activity` видно состояние соединений, в частности `idle in transaction`. Увеличивать `MaxPoolSize` — последнее средство, потому что это переносит проблему в базу. Если соединений действительно не хватает под реальную нагрузку, думать про PgBouncer и про сокращение времени, которое каждый запрос держит соединение.
>
> **EN:** First find who isn’t returning connections: typically open transactions, long-running queries, or a missing `Dispose`. `pg_stat_activity` shows connection states, notably `idle in transaction`. Raising `MaxPoolSize` is a last resort because it moves the problem into the database. If the load genuinely needs more connections, consider PgBouncer and reducing how long each request holds a connection.

> [!question]- Как увидеть, кто сейчас подключён к базе?
> **RU:** Через представление `pg_stat_activity`. Там по одной строке на каждый процесс сервера: пользователь, база, приложение, состояние, текущий запрос и время его начала. Клиентские соединения отличаются по `backend_type = 'client backend'`. Своё соединение можно найти по `pg_backend_pid()`.
>
> **EN:** Through the `pg_stat_activity` view. It has one row per server process: user, database, application, state, current query and its start time. Client connections have `backend_type = 'client backend'`. You can find your own connection via `pg_backend_pid()`.
