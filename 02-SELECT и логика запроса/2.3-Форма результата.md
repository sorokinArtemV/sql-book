# Форма результата: ORDER BY, LIMIT, DISTINCT

> [!abstract] SELECT и логика запроса · урок 3 из 5
> Учимся управлять формой ответа: почему без однозначного `ORDER BY` пагинация теряет строки, где оказываются `NULL` и как взять одну строку из группы через `DISTINCT ON`.

## Где мы

В [[2.1-Логический порядок выполнения SELECT|уроке 2.1]] мы разложили запрос на конвейер. Первые пять шагов решают, _какие_ строки попадут в ответ. Последние три — `DISTINCT`, `ORDER BY`, `LIMIT` — решают, _в каком виде_ ответ уйдёт клиенту: без повторов, в каком порядке и сколько штук.

Звучит как косметика. На практике именно здесь живут ошибки, которые доходят до прода незамеченными: список на сайте показывает одну и ту же запись на двух страницах, «последние уволенные» оказываются вовсе не уволенными, «текущий водитель» каждый раз разный. Запросы не падают. Они возвращают правдоподобный неправильный ответ.

Все три темы связаны одной мыслью: **порядок строк в SQL существует только там, где ты его явно задал, и только настолько, насколько ты его задал**.

## Без ORDER BY порядка нет

Начнём с того, что видно сразу:

```sql
SELECT id, created_at
FROM shipments
LIMIT 5;
```

**Что происходит.** Скорее всего вернутся строки с `id` 1, 2, 3, 4, 5, а `created_at` у них будут вразнобой — из 2024, 2026, снова 2024. Postgres читает таблицу с начала файла и отдаёт строки в том порядке, в каком они лежат на диске. Перевозки вставлялись в случайном порядке по дате, поэтому физический порядок совпадает с `id`, но не с `created_at`.

Слово «скорее всего» тут главное. Даже совпадение с `id` — случайность, а не правило. Таблица в Postgres — это куча (heap): строки лежат там, где нашлось место, без всякого порядка (подробно — глава 8). Что может перемешать результат, даже если данные не менялись:

- **UPDATE.** Новая версия строки записывается в другое место (подробно — 8.4). Строка с `id = 1` после обновления может оказаться в конце таблицы.
- **Параллельное чтение.** На большой таблице Postgres может читать её несколькими процессами. Каждый отдаёт свои строки, а итог склеивается в порядке готовности.
- **Синхронизированное сканирование.** Если одна сессия уже читает большую таблицу целиком, вторая сессия присоединяется к ней на текущей позиции, а не начинает с начала. Начало таблицы она дочитает в конце. Управляется параметром `synchronize_seqscans`, по умолчанию включён. «Большая» — это больше четверти `shared_buffers`.
- **Другой план.** Сегодня Postgres читает таблицу целиком, завтра — через индекс. Порядок разный.

Вывод один: если порядок важен, `ORDER BY` обязателен. Если `ORDER BY` нет, у Postgres нет обязательств, и полагаться на «у меня же всегда так выходило» нельзя.

## ORDER BY: базовые правила

```sql
SELECT id, customer_id, priority, created_at
FROM shipments
ORDER BY priority, created_at DESC
LIMIT 10;
```

**Что происходит.** Postgres сортирует сначала по `priority` по возрастанию. Внутри одинакового `priority` — по `created_at` по убыванию. `DESC` относится только к той колонке, после которой стоит, а не ко всему списку. Это частая ошибка чтения: `ORDER BY a, b DESC` — это «a по возрастанию, b по убыванию».

Отдельная деталь. `priority` — текст, и сортируется он по алфавиту: `critical`, `express`, `standard`. Так совпало, что алфавитный порядок совпадает со смысловым. Со `status` не повезло бы: `assigned`, `cancelled`, `created`, `delivered`, `in_transit` — по алфавиту, но не по жизненному циклу перевозки.

### Сортировка по выражению

`ORDER BY` принимает любое выражение, не только колонку:

```sql
SELECT id, picked_up_at, delivered_at,
       delivered_at - picked_up_at AS transit
FROM shipments
WHERE status = 'delivered'
ORDER BY delivered_at - picked_up_at DESC
LIMIT 10;
```

**Что происходит.** Postgres вычисляет разницу для каждой строки и сортирует по ней. Самые долгие доставки — сверху. Здесь можно было бы написать `ORDER BY transit DESC`: алиас в `ORDER BY` виден ([[2.1-Логический порядок выполнения SELECT|урок 2.1]]). А вот `ORDER BY transit * 2` уже не сработает — алиас допустим только голым именем.

Смысловой порядок статусов задаётся выражением через `CASE`:

```sql
SELECT id, status, created_at
FROM shipments
ORDER BY CASE status
             WHEN 'created'    THEN 1
             WHEN 'assigned'   THEN 2
             WHEN 'in_transit' THEN 3
             WHEN 'delivered'  THEN 4
             WHEN 'cancelled'  THEN 5
         END,
         created_at
LIMIT 20;
```

**Что происходит.** `CASE` превращает статус в число, сортировка идёт по числу. Сам `CASE` — тема [[2.4-Выражения|урока 2.4]], здесь важно только, что `ORDER BY` можно строить по вычисленному ключу.

Ещё одна форма — `ORDER BY 2`, номер колонки из `SELECT`. Работает, но ломается молча, когда кто-то добавит колонку в начало `SELECT`. В коде, который живёт дольше одного вечера, не используй.

## NULL в сортировке: «последние уволенные»

Задача: показать пять последних уволенных водителей.

```sql
SELECT id, full_name, status, terminated_at
FROM drivers
ORDER BY terminated_at DESC
LIMIT 5;
```

**Что происходит.** Вернутся пять водителей со статусом `active` или `on_leave` и `terminated_at = ∅`. Ни одного уволенного. Причина: при сортировке Postgres считает `NULL` _больше_ любого значения. При `ASC` они уходят в конец, при `DESC` — в начало. У 92 % водителей `terminated_at` пустой, и они заняли весь верх.

Это прямое продолжение прошлого урока: в `ORDER BY` `NULL` не «неизвестен», а «стоит рядом с другими `NULL`» (таблица «Где NULL равны друг другу» из [[2.2-NULL и трёхзначная логика|2.2]]).

Починить можно двумя способами:

```sql
-- Способ 1: явно указать, где NULL
SELECT id, full_name, status, terminated_at
FROM drivers
ORDER BY terminated_at DESC NULLS LAST
LIMIT 5;

-- Способ 2: убрать NULL фильтром — если они по смыслу не нужны
SELECT id, full_name, status, terminated_at
FROM drivers
WHERE terminated_at IS NOT NULL
ORDER BY terminated_at DESC
LIMIT 5;
```

**Что происходит.** В первом варианте `NULLS LAST` переносит пустые значения в конец, и сверху оказываются реально уволенные. Во втором неуволенные вообще не участвуют. Для этой задачи второй честнее: «последние уволенные» — это по смыслу только уволенные. `NULLS FIRST / LAST` нужен, когда `NULL` в результате должны остаться, но в другом месте.

|Сортировка|Где NULL по умолчанию|Как поменять|
|---|---|---|
|`ASC`|в конце|`NULLS FIRST`|
|`DESC`|в начале|`NULLS LAST`|

В других базах по-разному: в SQL Server и MySQL `NULL` считается _меньше_ любого значения. Если переносишь запрос оттуда, порядок `NULL` перевернётся.

## LIMIT, OFFSET и FETCH FIRST

`LIMIT n` отдаёт первые n строк результата. `OFFSET m` пропускает первые m. Вместе — страница:

```sql
SELECT id, shipment_id, amount, currency, issued_at
FROM invoices
ORDER BY issued_at DESC
LIMIT 20 OFFSET 40;   -- третья страница по 20
```

У этой записи есть стандартный эквивалент:

```sql
SELECT id, shipment_id, amount, currency, issued_at
FROM invoices
ORDER BY issued_at DESC
OFFSET 40 ROWS
FETCH FIRST 20 ROWS ONLY;
```

**Что происходит.** Оба запроса делают одно и то же. `LIMIT` — расширение Postgres и MySQL, `FETCH FIRST` — из стандарта SQL, его понимают и Oracle, и SQL Server. Писать можно как удобно, в Postgres разницы нет.

У `FETCH FIRST` есть один вариант, которого нет у `LIMIT`:

```sql
SELECT id, shipment_id, amount, currency, issued_at
FROM invoices
ORDER BY issued_at DESC
FETCH FIRST 1 ROWS WITH TIES;
```

**Что происходит.** `WITH TIES` — «и всех, кто делит последнее место». Сортировка по `issued_at DESC`, первая строка — счёт за самую позднюю дату. Но в эту же дату выставлено ещё несколько сотен счетов с тем же `issued_at`. `WITH TIES` вернёт их все. Получается «все счета за последний день выставления» одним запросом без подзапроса. Работает только с `ORDER BY` — без него непонятно, что считать «ничьей». `WITH TIES` появился в PostgreSQL 13.

## Центральный конфликт: пагинация теряет строки

Теперь главное в уроке. Запрос выше — `ORDER BY issued_at DESC LIMIT 20 OFFSET n` — выглядит как нормальная пагинация. Он ломается.

`issued_at` — это `date`. В одну дату выставляется несколько сотен счетов. Для Postgres все они _равны_ по ключу сортировки. В каком порядке они встанут относительно друг друга — не определено. Сортировка не обязана быть стабильной, и при каждом запуске порядок внутри «ничьей» может быть разным.

Пагинация — это несколько _независимых_ запросов. Каждая страница — новый запуск, новая сортировка, свой порядок внутри одинаковых дат. Если граница страницы проходит посреди группы одинаковых дат, получается вот что:

![[2.3-pagination-ties.png]]
*Рис. 2.3.1. Каждая страница — отдельная сортировка. Строки с одинаковым ключом могут поменяться местами между запросами, и граница страницы их режет по-разному.*

Пользователь листает список счетов. На первой странице видит счёт 502. На второй — снова 502. Счёт 503 он не видит никогда. Запрос не падает, ошибки в логах нет.

Почему это вообще может меняться между запусками при одних и тех же данных — всё то же, что в начале урока: параллельное чтение, синхронизированное сканирование, другой алгоритм сортировки под другой `LIMIT`. Например, для первой страницы Postgres выберет top-N heapsort ([[2.1-Логический порядок выполнения SELECT|урок 2.1]]), для пятидесятой — полную сортировку. Это разные алгоритмы, и одинаковые ключи они расставляют по-разному.

### Как починить

Сделать ключ сортировки уникальным. Добавить в конец колонку, которая гарантированно различает строки, — обычно первичный ключ:

```sql
SELECT id, shipment_id, amount, currency, issued_at
FROM invoices
ORDER BY issued_at DESC, id DESC
LIMIT 20 OFFSET 20;
```

**Что происходит.** Внутри одной даты счета теперь упорядочены по `id`. Ничьих больше нет: две строки с одинаковым `(issued_at, id)` невозможны, потому что `id` уникален. Порядок полностью определён, и каждая страница режет один и тот же список в одних и тех же местах.

Правило: **пагинация требует уникального `ORDER BY`**. Не «обычно уникального», не «на практике там почти нет повторов» — уникального по построению. `created_at` типа `timestamptz` тоже не уникален: две строки, вставленные в одной транзакции, получают одинаковое `now()`.

### Вторая проблема пагинации: данные меняются между страницами

Даже с уникальным порядком `OFFSET` уязвим к изменениям. Пользователь открыл первую страницу. Пока он её читал, выставили новый счёт — он встал на первое место. Теперь всё сдвинулось на одну позицию, и последний счёт первой страницы стал первым на второй. Пользователь увидит его дважды.

`OFFSET` говорит «пропусти 20 строк», а не «продолжи после такого-то счёта». Второй вариант называется keyset-пагинацией (seek): `WHERE (issued_at, id) < (последняя_дата, последний_id)`. Она не боится вставок и не тормозит на дальних страницах. Подробный разбор — в 10.7, вместе с индексами, без которых она не раскрывается.

## Сколько стоит OFFSET

Последнее про `OFFSET` — производительность. Логически `OFFSET 100000` значит «пропусти». Физически пропустить нельзя, не прочитав. Postgres должен найти, отсортировать и выбросить сто тысяч строк, чтобы отдать двадцать.

![[2.3-offset-cost.png]]
*Рис. 2.3.2. Стоимость страницы с OFFSET растёт линейно с номером страницы. Первая страница дешёвая, тысячная — дорогая.*

Пока таблица маленькая, это незаметно. На миллионах строк дальние страницы начинают тормозить, а боты, которые обходят сайт до последней страницы, кладут базу. Лечится keyset-пагинацией (10.7) или запретом глубоких страниц на уровне продукта — как делают поисковики, показывая максимум несколько сотен результатов.

## DISTINCT: убрать повторяющиеся строки

`DISTINCT` после `SELECT` убирает строки-дубликаты из результата.

```sql
SELECT DISTINCT origin_country
FROM shipments
ORDER BY origin_country;
```

**Что происходит.** 300 000 перевозок сворачиваются в 24 строки — по одной на страну отправления. `DISTINCT` применяется ко _всей строке_ результата, а не к первой колонке.

```sql
SELECT DISTINCT origin_country, priority
FROM shipments
ORDER BY origin_country, priority;
```

**Что происходит.** Теперь уникальны _пары_ «страна + приоритет». Строк будет до 72 (24 страны × 3 приоритета). Частая ошибка новичка — думать, что `DISTINCT` относится только к колонке сразу после него. Это не так: `DISTINCT a, b` — уникальные комбинации `(a, b)`.

### DISTINCT и GROUP BY — одно и то же

```sql
SELECT DISTINCT origin_country FROM shipments;
SELECT origin_country FROM shipments GROUP BY origin_country;
```

**Что происходит.** Результат одинаковый, и планировщик обычно строит для них одинаковый план. `DISTINCT` — это `GROUP BY` по всем колонкам `SELECT` без агрегатов. Если нужны ещё и подсчёты, пиши `GROUP BY`. Если просто уникальные значения — `DISTINCT` читается лучше.

### DISTINCT как пластырь

Если в запросе с `JOIN` появились дубли и ты добавил `DISTINCT`, чтобы они исчезли, — остановись. Почти всегда это значит, что `JOIN` размножил строки (fan-out), и `DISTINCT` маскирует ошибку в логике. Дубли пропали, но суммы и количества в соседних запросах будут врать. Разбор — в 3.3. Правило: `DISTINCT` ставят, когда _знают_, откуда повторы и что они не нужны по смыслу, а не когда «что-то задвоилось».

## DISTINCT ON: одна строка из каждой группы

Теперь задача, которая встречается постоянно: «для каждой перевозки — текущее назначение». В таблице `assignments` хранится вся история: у 15 % перевозок два назначения, первое снято с причиной `reassigned`. Нужно для каждой `shipment_id` взять одну строку — самую позднюю.

`GROUP BY` тут не помогает: он даст `max(assigned_at)`, но не остальные колонки этой строки ([[2.1-Логический порядок выполнения SELECT|урок 2.1]], колонка вне `GROUP BY`). Обычный `DISTINCT` тоже: он убирает только полностью одинаковые строки.

В Postgres для этого есть `DISTINCT ON`:

```sql
SELECT DISTINCT ON (shipment_id)
       shipment_id, driver_id, truck_id, assigned_at
FROM assignments
ORDER BY shipment_id, assigned_at DESC;
```

**Что происходит.** Postgres сортирует строки по `shipment_id`, внутри — по `assigned_at` от новых к старым. Потом идёт по отсортированному списку и из каждой группы с одинаковым `shipment_id` берёт первую строку. Первая — самая поздняя, потому что так задан `ORDER BY`. Остальные строки группы выбрасываются.

![[2.3-distinct-on.png]]
*Рис. 2.3.3. DISTINCT ON сам не знает, какая строка «лучшая». Это решает ORDER BY после ключа группы.*

### Правила DISTINCT ON

**Ключ группы должен стоять в начале ORDER BY.**

```sql
SELECT DISTINCT ON (shipment_id) shipment_id, driver_id, assigned_at
FROM assignments
ORDER BY assigned_at DESC;
-- ERROR:  SELECT DISTINCT ON expressions must match initial ORDER BY expressions
```

**Что происходит.** Чтобы найти «первую строку в группе», Postgres сначала должен собрать группу подряд — для этого сортировка обязана начинаться с ключа группы. Хочешь, чтобы итоговый результат был отсортирован иначе, например по дате, — оберни в подзапрос и отсортируй снаружи.

**Без ORDER BY первая строка случайна.** `DISTINCT ON (shipment_id)` без сортировки по `assigned_at` вернёт какое-то одно назначение на перевозку. Какое — не определено. Это та же ловушка, что `LIMIT` без `ORDER BY`, только на уровне каждой группы.

**Ничьи внутри группы.** Если у двух назначений одной перевозки одинаковый `assigned_at`, «первым» окажется любое из них. Нужен уникальный хвост: `ORDER BY shipment_id, assigned_at DESC, id DESC`. Правило то же, что для пагинации.

Ещё пример — последнее GPS-событие по первой тысяче перевозок:

```sql
SELECT DISTINCT ON (shipment_id)
       shipment_id, occurred_at, event_type, lat, lon
FROM tracking_events
WHERE shipment_id <= 1000
ORDER BY shipment_id, occurred_at DESC, id DESC;
```

**Что происходит.** Фильтр по `shipment_id` сужает 2,5 млн событий до нескольких тысяч. Индекса на `shipment_id` нет, поэтому Postgres всё равно прочитает таблицу целиком — но сортировать будет только отобранное. Хвост `id DESC` разрешает ничьи от дубликатов GPS-событий, которые специально заложены в базу.

`DISTINCT ON` — расширение Postgres, в стандарте SQL его нет. В других базах ту же задачу решают через `ROW_NUMBER()` в подзапросе. Этот вариант мы разберём в 6.2 и сравним.

## Место в конвейере: уточняем модель

В [[2.1-Логический порядок выполнения SELECT|2.1]] мы поставили `DISTINCT` шестым шагом, до `ORDER BY`. Для обычного `DISTINCT` это верно: дубли убираются, потом результат сортируется.

Для `DISTINCT ON` это упрощение. Чтобы выбрать первую строку в группе, нужен порядок, а порядок задаёт `ORDER BY`. Поэтому физически Postgres сначала сортирует, потом выбирает. Логически можно думать так: `ORDER BY` в запросе с `DISTINCT ON` работает дважды — сначала решает, какая строка в группе первая, потом упорядочивает итоговый результат. Модель конвейера остаётся верной для всего остального.

## Как устроено: сортировка и work_mem

Сортировка — одна из самых затратных операций в запросе. Postgres выбирает для неё один из трёх способов, и они видны в `EXPLAIN ANALYZE` в строке `Sort Method`:

|Sort Method|Когда|Что делает|
|---|---|---|
|`quicksort`|данные помещаются в `work_mem`|сортирует в памяти|
|`top-N heapsort`|есть `LIMIT` и он небольшой|держит в памяти только N лучших строк ([[2.1-Логический порядок выполнения SELECT\|урок 2.1]])|
|`external merge`|данные не помещаются в `work_mem`|режет на куски, сортирует их на диске, сливает|

`work_mem` — память, которую одна операция сортировки или хэширования может взять до того, как пойдёт на диск. По умолчанию 4 МБ. Это мало, и на большой таблице сортировка всего результата почти всегда уходит на диск:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, speed_kmh
FROM tracking_events
ORDER BY speed_kmh;
```

Типичный вид, план может отличаться, смотри на форму, а не на числа:

```text
Sort
  Sort Key: speed_kmh
  Sort Method: external merge  Disk: ...kB
  ->  Seq Scan on tracking_events
```

**Что происходит.** 2,5 млн строк не влезают в 4 МБ, Postgres пишет промежуточные куски во временные файлы и потом сливает их. Это медленнее, чем в памяти, но работает при любом объёме. Если увеличить `work_mem` для сессии (`SET work_mem = '256MB'`), тот же запрос переключится на `quicksort`. На проде это настраивают аккуратно: `work_mem` выделяется на _каждую_ операцию в _каждом_ запросе, и сто одновременных запросов с большим `work_mem` могут съесть всю память сервера.

Самый дешёвый способ сортировки — не сортировать. Если есть индекс по колонке `ORDER BY`, Postgres может просто пройти по индексу: строки оттуда выходят уже упорядоченными. В связке с `LIMIT` это даёт «прочитать 20 строк и остановиться». Это тема 9.9.

`DISTINCT` и `DISTINCT ON` устроены через ту же сортировку. Типичный план для текущих назначений:

```text
Unique
  ->  Sort
        Sort Key: shipment_id, assigned_at DESC
        ->  Seq Scan on assignments
```

**Что происходит.** `Sort` упорядочивает 330 000 назначений. `Unique` идёт по отсортированному потоку и пропускает строку, только если её ключ отличается от предыдущей. Для обычного `DISTINCT` Postgres может вместо этого выбрать `HashAggregate` — собрать уникальные значения в хэш-таблицу без сортировки. Для `DISTINCT ON` нужен именно порядок, поэтому там почти всегда `Sort` + `Unique`.

## Где ломается

**LIMIT без ORDER BY.** Возвращает какие-то строки. Сегодня одни, после `UPDATE`, `VACUUM` или смены плана — другие.

**Пагинация по неуникальному ключу.** Строки дублируются между страницами и теряются. Чинится уникальным хвостом в `ORDER BY`, обычно первичным ключом.

**NULL в начале при DESC.** «Последние по дате» оказываются строками без даты. Решение: `NULLS LAST` или фильтр `IS NOT NULL`.

**`DESC` относится к одной колонке.** `ORDER BY a, b DESC` — это `a ASC, b DESC`.

**DISTINCT на несколько колонок.** Уникальны комбинации, а не первая колонка.

**DISTINCT как пластырь после JOIN.** Маскирует размножение строк. Глава 3.3.

**DISTINCT ON без полного ORDER BY.** Без сортировки внутри группы или с ничьими — случайная строка из группы.

**ORDER BY в подзапросе.** `SELECT * FROM (SELECT ... ORDER BY x) t` не гарантирует, что внешний результат будет отсортирован по `x`. Порядок гарантирует только `ORDER BY` самого внешнего запроса. Postgres часто сохраняет внутренний порядок, поэтому ловушка проявляется редко — и внезапно, например после `JOIN` во внешнем запросе.

**Глубокий OFFSET.** Медленно растёт с номером страницы и уязвим к вставкам между запросами.

> [!example] Мост в .NET
> В LINQ всё то же самое, только скрыто:
>
> ```csharp
> var page = await db.Invoices
>     .OrderByDescending(i => i.IssuedAt)
>     .ThenByDescending(i => i.Id)
>     .Skip(20)
>     .Take(20)
>     .ToListAsync();
> ```
>
> **Что происходит.** `OrderByDescending` и `ThenByDescending` дают `ORDER BY issued_at DESC, id DESC`, `Skip` и `Take` — `OFFSET` и `LIMIT`. Если забыть `ThenByDescending(i => i.Id)`, получится ровно та ловушка с пагинацией, что выше. EF Core её не заметит.
>
> Зато он замечает отсутствие сортировки вообще: если написать `Skip`/`Take` без `OrderBy`, EF Core пишет в лог предупреждение о том, что ограничение строк без сортировки может дать непредсказуемый результат. Это предупреждение `RowLimitingOperationWithoutOrderByWarning`. Не отключай его — это ровно ловушка `LIMIT` без `ORDER BY`.
>
> Порядок `NULL` EF Core не подгоняет под C#. В LINQ to Objects `null` при сортировке меньше любого значения, в Postgres — больше. Значит, `OrderByDescending(d => d.TerminatedAt)` в памяти и в базе даст разный порядок. EF Core 10 генерирует просто `ORDER BY terminated_at DESC`, без `NULLS LAST`.
>
> `Distinct()` транслируется в `DISTINCT`. Для `DISTINCT ON` прямого метода в LINQ нет. Задачу «последнее назначение для каждой перевозки» в EF Core пишут так:
>
> ```csharp
> var current = await db.Assignments
>     .GroupBy(a => a.ShipmentId)
>     .Select(g => g.OrderByDescending(a => a.AssignedAt).First())
>     .ToListAsync();
> ```
>
> EF Core переводит это в подзапрос с `ROW_NUMBER()`, присоединённый через `LEFT JOIN` к списку групп, а не в `DISTINCT ON`. Если нужен именно `DISTINCT ON` — сырой SQL через `FromSql` или Dapper (глава 15).

## Глубже / на синьора

**Collation и порядок строк.** Как сортируется текст, зависит от collation — правил сравнения для языка. В образе `postgres:18` по умолчанию `en_US.utf8`: регистр и диакритика при сравнении учитываются хитро, `'apple' < 'Banana'` истинно. В collation `"C"` сравнение идёт по байтам: все заглавные раньше всех строчных. `ORDER BY name COLLATE "C"` — быстрее и предсказуемее, но не по-человечески. На проде отдельная боль: смена версии `glibc` на сервере может поменять порядок сортировки и сломать индексы по тексту. Именно поэтому в Postgres появились встроенные провайдеры collation.

**Incremental Sort.** Если данные уже частично отсортированы — например, по индексу на `shipment_id`, а нужно `ORDER BY shipment_id, assigned_at` — Postgres может досортировать только внутри каждой группы, а не всё целиком. В плане это узел `Incremental Sort`. Появился в PostgreSQL 13.

**Сортировка стабильна?** Нет, и это не баг. Стандарт SQL не требует стабильности, и алгоритмы Postgres её не дают. Единственный способ получить детерминированный порядок — уникальный ключ сортировки.

**LIMIT в подзапросе меняет смысл.** `ORDER BY` + `LIMIT` внутри подзапроса — законный способ «взять топ-N, потом что-то с ним сделать». Здесь порядок внутри подзапроса имеет смысл, потому что определяет, какие строки попадут в N. Ловушка с `ORDER BY` в подзапросе — только про порядок _вывода_.

**Случайная выборка.** `ORDER BY random() LIMIT 10` работает, но сортирует всю таблицу. На больших таблицах для приблизительной выборки есть `TABLESAMPLE` — читает случайные страницы, а не все строки.

- Порядок без ORDER BY не гарантирован — 🔴 спрашивают почти всегда, часто как «почему у нас в тестах порядок плавает».
- Пагинация без уникального ORDER BY — 🔴, классика.

- DISTINCT ON и «последняя запись в группе» — 🔴 как задача; конкретно DISTINCT ON — 🟡, часто примут и решение через ROW_NUMBER.
- DISTINCT против GROUP BY — 🟡.
- Sort Method и work_mem — 🟡 на Middle+.
- FETCH FIRST … WITH TIES, collation, Incremental Sort — ⚪.

## На собесе

> [!question]- Гарантирован ли порядок строк без ORDER BY?
> **RU:** Нет. Таблица в Postgres — куча без порядка, и строки выходят в том порядке, в каком их отдал план. Порядок меняется после UPDATE, потому что новая версия строки пишется в другое место, при параллельном чтении, при синхронизированном сканировании, при смене плана. Если порядок нужен, ORDER BY обязателен — и он должен быть однозначным.
>
> **EN:** No. A Postgres table is an unordered heap, and rows come out in whatever order the plan produces them. Order changes after an UPDATE because the new row version lands elsewhere, under parallel scans, synchronized scans, or a plan change. If order matters, ORDER BY is mandatory — and it must be unambiguous.

> [!question]- Почему пагинация через ORDER BY created_at LIMIT OFFSET может показывать одну строку дважды и терять другие?
> **RU:** Потому что created_at не уникален, а сортировка не стабильна. Строки с одинаковым ключом могут встать в разном порядке при каждом запросе, а каждая страница — отдельный запрос. Если граница страницы проходит через такую группу, одна строка попадает на обе страницы, а другая ни на одну. Решение — добавить уникальный хвост, обычно `ORDER BY created_at, id`. Плюс OFFSET съезжает, если между запросами вставили новые строки, — от этого лечит keyset-пагинация.
>
> **EN:** Because created_at isn’t unique and sorting isn’t stable. Rows with equal keys may come back in a different order on every execution, and each page is a separate query. If a page boundary cuts through such a group, one row lands on both pages and another on neither. The fix is a unique tiebreaker, typically `ORDER BY created_at, id`. OFFSET also shifts when rows are inserted between requests, which keyset pagination solves.

> [!question]- Как выбрать последнюю запись в каждой группе?
> **RU:** В Postgres проще всего через DISTINCT ON: `SELECT DISTINCT ON (group_key) ... ORDER BY group_key, created_at DESC`. Postgres сортирует строки, собирает группы подряд и берёт из каждой первую, а «первую» определяет ORDER BY. ORDER BY обязан начинаться с ключа группы и должен быть однозначным внутри группы. Переносимый вариант — ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...) в подзапросе и фильтр rn = 1.
>
> **EN:** In Postgres the shortest way is DISTINCT ON: `SELECT DISTINCT ON (group_key) ... ORDER BY group_key, created_at DESC`. Postgres sorts the rows, groups them contiguously, and keeps the first of each group, where “first” is defined by ORDER BY. ORDER BY must start with the group key and be unambiguous within a group. The portable version is ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...) in a subquery filtered on rn = 1.

> [!question]- Где оказываются NULL при сортировке?
> **RU:** Postgres считает NULL больше любого значения: при ASC они в конце, при DESC — в начале. Отсюда частая ошибка: «последние по дате» через ORDER BY date DESC возвращают строки без даты. Порядок меняется через NULLS FIRST / NULLS LAST. В SQL Server и MySQL наоборот — NULL меньше любого значения, это важно при переносе запросов.
>
> **EN:** Postgres treats NULL as greater than any value: last with ASC, first with DESC. That’s why “latest by date” via ORDER BY date DESC often returns rows with no date. You control it with NULLS FIRST / NULLS LAST. SQL Server and MySQL do the opposite — NULL sorts as the smallest — which matters when porting queries.

> [!question]- Почему OFFSET медленный на дальних страницах?
> **RU:** Потому что пропустить строки, не прочитав их, нельзя. OFFSET 100000 LIMIT 20 заставляет Postgres найти, отсортировать и выбросить сто тысяч строк, чтобы отдать двадцать. Стоимость растёт линейно с номером страницы. Альтернатива — keyset-пагинация: запоминаешь ключ последней строки и просишь строки после него, а с индексом по ключу это стоит одинаково на любой странице.
>
> **EN:** Because you can’t skip rows without reading them. OFFSET 100000 LIMIT 20 makes Postgres find, sort and discard a hundred thousand rows to return twenty. Cost grows linearly with page number. The alternative is keyset pagination: remember the last row’s key and ask for rows after it, which with an index on that key costs the same on any page.

## Промпт для агента практики

**Куда:** в текущую сессию агента практики.

> [!example]- Промпт целиком
> ```text
> Урок: 2.3 Форма результата: ORDER BY, LIMIT, DISTINCT
>
> Навыки, которые надо отработать:
> - отсортировать по нескольким колонкам с разным направлением и по вычисленному
>   выражению
> - задать смысловой порядок текстовых значений, который не совпадает с
>   алфавитным
> - поставить строки с отсутствующим значением в нужное место сортировки или
>   исключить их
> - написать постраничную выдачу с гарантированно однозначным порядком
> - вернуть «топ-N с ничьими» — всех, кто делит последнее место
> - получить уникальные значения и уникальные комбинации нескольких колонок
> - выбрать одну строку из каждой группы по правилу «самая поздняя / самая
>   большая» через DISTINCT ON
>
> Ловушки, на которые нужны задачи:
> - пагинация по неуникальному ключу: данные должны содержать группу строк с
>   одинаковым значением ключа сортировки, через которую проходит граница
>   страницы; наивное решение без уникального хвоста формально даёт результат,
>   но порядок внутри группы не определён — попроси читателя объяснить, почему
>   это ошибка, даже если результат совпал с эталоном
> - NULL в начале при DESC: задача «последние N по дате» на nullable-колонке,
>   где NULL много; неверное решение возвращает строки без даты
> - DESC применяется к одной колонке: задача с сортировкой по двум колонкам в
>   противоположных направлениях
> - DISTINCT по нескольким колонкам: задача, где читатель ждёт уникальность по
>   первой колонке, а получает комбинации
> - DISTINCT ON с неполным ORDER BY: данные должны содержать группу, где у двух
>   строк одинаковое значение второго ключа сортировки; неверное решение
>   выбирает строку случайно
> - DISTINCT ON с ORDER BY, который не начинается с ключа группы: решение падает
>   с ошибкой, читатель должен знать, как переписать
> - LIMIT без ORDER BY: одна короткая задача «первые N»
>
> Задачи на запросы (учебные домены):
> - 5 задач, от простой к сложной
> - типы: многоколоночная сортировка с выражением; смысловой порядок статусов;
>   страница N с однозначным порядком; топ-N с ничьими; последняя запись в
>   каждой группе
> - 1 задача на время, 10–15 минут
> - если в данных нет случая для ловушки — добавь строки и скажи, что добавил
> - задачи с JOIN не давать, только одна таблица или уже готовая выборка (JOIN —
>   глава 3)
>
> Эксперименты на freight:
> - выполнить EXPLAIN ANALYZE для трёх запросов к tracking_events: ORDER BY
>   speed_kmh без LIMIT; ORDER BY speed_kmh LIMIT 10; то же без LIMIT после SET
>   work_mem = '256MB' → найти Sort Method в каждом → должны увидеть external
>   merge, top-N heapsort и quicksort; в конце RESET work_mem
> - выполнить EXPLAIN ANALYZE для invoices ORDER BY issued_at DESC, id DESC с
>   OFFSET 0 LIMIT 20 и с OFFSET 200000 LIMIT 20 → сравнить время и Sort Method
>   → увидеть, что дальняя страница дороже
> - выполнить EXPLAIN для DISTINCT ON на assignments → найти узлы Sort и Unique
>
> Повторение:
> - подмешай 1 задачу на NULL и трёхзначную логику (урок 2.2) или на темы из
>   журнала ошибок
> ```
