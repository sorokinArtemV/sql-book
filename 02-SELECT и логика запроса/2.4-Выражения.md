# Выражения: CASE, приведение типов, LIKE и регулярные выражения

> [!abstract] SELECT и логика запроса · урок 4 из 5
> Три инструмента для логики внутри строки — `CASE`, приведение типов и поиск по шаблону — и ловушки на их стыках: целочисленное деление, числа в тексте и потерянный индекс.

## Где мы

Предыдущие уроки были про строки целиком: какие отобрать, как упорядочить, сколько отдать. Этот урок — про то, что происходит _внутри_ одной строки. Как превратить вес в категорию «лёгкий / средний / тяжёлый». Как сравнить число с текстом. Как найти клиентов, в названии которых есть «logistics».

Три инструмента:

- **CASE** — условие прямо в выражении, аналог `switch` или тернарного оператора в C#;
- **приведение типов** — `::` и `CAST`, явное превращение одного типа в другой и неявное, которое Postgres делает сам;
- **LIKE, ILIKE и регулярные выражения** — поиск по шаблону в тексте.

По отдельности всё это простое. Ловушки возникают на стыках: CASE и NULL, деление целых чисел, текст, который выглядит как число. И в одном месте — производительность: от того, как записано выражение, зависит, сможет ли Postgres использовать индекс. Индексы будут в главе 9, но заложить понимание надо здесь.

## CASE: условие внутри выражения

`CASE` возвращает значение в зависимости от условий. Используется везде, где допустимо выражение: в `SELECT`, `WHERE`, `ORDER BY`, `GROUP BY`, внутри функций.

### Две формы

**Поисковая форма** — с полными условиями. Основная, пиши её по умолчанию:

```sql
SELECT id, weight_kg,
       CASE
           WHEN weight_kg >= 10000 THEN 'heavy'
           WHEN weight_kg >= 1000  THEN 'medium'
           ELSE 'light'
       END AS weight_class
FROM shipments
LIMIT 10;
```

**Что происходит.** Для каждой строки Postgres проверяет условия сверху вниз. Первое, которое дало `TRUE`, определяет результат, остальные даже не проверяются. Перевозка на 15 000 кг подходит под оба первых условия, но получит `heavy`, потому что первое сработало раньше.

**Простая форма** — сравнение одного выражения со списком значений:

```sql
SELECT id, priority,
       CASE priority
           WHEN 'critical' THEN 'в течение суток'
           WHEN 'express'  THEN 'до трёх дней'
           ELSE 'по графику'
       END AS sla
FROM shipments
LIMIT 10;
```

**Что происходит.** Это сокращение для `WHEN priority = 'critical'`, `WHEN priority = 'express'`. Удобно для перечислений. Но внутри — обычное `=`, и это скоро станет важным.

![[2.4-case-flow.png]]
*Рис. 2.4.1. Условия проверяются по порядку, первое TRUE побеждает. NULL в условии — это не TRUE, CASE идёт дальше. Без ELSE результат NULL.*

### Ловушка порядка

Порядок WHEN — часть логики. Переставь условия, и категория `heavy` пропадёт:

```sql
SELECT CASE
           WHEN weight_kg >= 1000  THEN 'medium'
           WHEN weight_kg >= 10000 THEN 'heavy'
           ELSE 'light'
       END AS weight_class,
       count(*)
FROM shipments
GROUP BY weight_class;
```

**Что происходит.** Любой вес от 10 000 кг больше 1000, поэтому первое условие ловит всех тяжёлых и записывает их в `medium`. До второго WHEN они не доходят. В результате две категории вместо трёх, ошибки нет. Правило: в цепочке диапазонов условия идут от самого узкого к самому широкому, либо границы задаются с двух сторон (`weight_kg >= 1000 AND weight_kg < 10000`).

Кстати, тут `GROUP BY weight_class` — по алиасу. Это то расширение Postgres, о котором говорили в «Глубже» [[2.1-Логический порядок выполнения SELECT|урока 2.1]]. С правильным порядком условий получится примерно треть лёгких, 40 % средних и четверть тяжёлых — распределение весов в базе скошено к малым значениям.

### Ловушка: простой CASE и NULL

Хотим пометить перевозки без диспетчера:

```sql
SELECT id, dispatcher_id,
       CASE dispatcher_id
           WHEN NULL THEN 'не назначен'
           ELSE 'назначен'
       END AS state
FROM shipments
WHERE status = 'created'
LIMIT 5;
```

**Что происходит.** Все пять строк получат `назначен`, хотя у всех `dispatcher_id` пустой. Простая форма раскрывается в `WHEN dispatcher_id = NULL`, а `= NULL` всегда даёт `NULL` ([[2.2-NULL и трёхзначная логика|урок 2.2]]). Условие никогда не срабатывает, CASE уходит в ELSE. Проверку на NULL можно сделать только в поисковой форме: `WHEN dispatcher_id IS NULL THEN ...`.

### Тип результата

У `CASE` один тип результата на все строки, как у `COALESCE`:

```sql
SELECT CASE WHEN dispatcher_id IS NULL THEN 'не назначен'
            ELSE dispatcher_id
       END
FROM shipments
LIMIT 5;
-- ERROR:  invalid input syntax for type integer: "не назначен"
```

**Что происходит.** Postgres смотрит на все ветки: одна `integer`, другая — литерал без типа. Он решает, что результат `integer`, и пытается превратить `'не назначен'` в число. Решение то же, что в [[2.2-NULL и трёхзначная логика|2.2]]: `ELSE dispatcher_id::text`. Тип определяется до чтения данных, поэтому ошибка будет даже на пустой таблице.

### CASE в ORDER BY, WHERE и внутри агрегатов

В `ORDER BY` мы уже использовали `CASE` для смыслового порядка статусов ([[2.3-Форма результата|урок 2.3]]). Внутри агрегата он даёт условный подсчёт:

```sql
SELECT count(*) AS total,
       sum(CASE WHEN status = 'delivered' THEN 1 ELSE 0 END) AS delivered
FROM shipments;
```

**Что происходит.** Для каждой строки `CASE` даёт 1 или 0, `sum` их складывает. Получается количество доставленных без отдельного запроса. Это зачаток условной агрегации, в 4.4 разберём её целиком вместе с `FILTER`, который делает то же короче.

В `WHERE` `CASE` писать можно, но почти всегда не нужно: `CASE` в условии почти всегда переписывается через `AND` и `OR`, и такой вариант планировщик понимает лучше. Видишь `WHERE CASE ... END = 1` — скорее всего, его можно упростить.

## Приведение типов: явное и неявное

### Явное: :: и CAST

Две записи одного и того же:

```sql
SELECT '42'::integer,
       CAST('42' AS integer);
```

**Что происходит.** Обе превращают строку `'42'` в число 42. `CAST(... AS ...)` — стандарт SQL, `::` — сокращение Postgres. В Postgres пиши `::`, оно короче. В коде, который должен работать на нескольких базах, — `CAST`.

Если превратить нельзя — ошибка, а не `NULL`:

```sql
SELECT 'abc'::integer;
-- ERROR:  invalid input syntax for type integer: "abc"
```

**Что происходит.** `'abc'` нельзя прочитать как число, и запрос падает целиком.

### Неявное: литерал подстраивается

Строковый литерал в кавычках изначально не имеет типа. Postgres даёт ему тип по контексту:

```sql
SELECT '17' + 1;          -- 18
SELECT '17'::text + 1;    -- ERROR:  operator does not exist: text + integer
```

**Что происходит.** В первом запросе `'17'` — литерал без типа. Postgres видит `+` с целым числом и решает, что литерал — тоже целое. Во втором ты сам сказал, что это `text`. Оператора «текст плюс число» в Postgres нет, и неявно превращать текст в число он не станет.

Postgres строже многих баз. MySQL, например, сложит `'17abc' + 1` и вернёт 18 с предупреждением. Postgres неявно приводит только «безопасные» пары: целое в более широкое целое, целое в `numeric`, `numeric` в `float`. Всё, где можно потерять данные или смысл, — только явно.

### Кто к кому подстраивается при сравнении

Вот где это начинает влиять на производительность. Сравним два почти одинаковых фильтра:

```sql
SELECT * FROM shipments WHERE customer_id = '17';
SELECT * FROM shipments WHERE customer_id = 17.0;
```

**Что происходит.** Оба вернут перевозки клиента 17. Но работают по-разному.

![[2.4-cast-literal-vs-column.png]]
*Рис. 2.4.2. Когда типы разные, Postgres приводит одну сторону к другой. Если приводится колонка — это работа в каждой строке и потеря индекса.*

В первом случае литерал без типа превращается в `integer` один раз, при разборе запроса. Сравнивается `integer` с `integer` — как если бы ты написал `= 17`.

Во втором `17.0` — литерал типа `numeric`. Оператора «целое равно numeric» нет. Postgres приводит `customer_id` к `numeric` — и делает это для каждой строки. Сейчас это незаметно: индекса на `customer_id` нет, таблица всё равно читается целиком. Когда индекс появится (глава 9), он будет построен по `integer`. Для условия по `numeric` он не подойдёт, и Postgres опять прочитает всю таблицу.

То же самое происходит, когда ты сам приводишь колонку: `WHERE customer_id::text = '17'`. Правило на всю книгу: **приводи значение к типу колонки, а не колонку к типу значения**.

### Целочисленное деление

Классическая ошибка в отчётах — доля доставленных:

```sql
SELECT sum(CASE WHEN status = 'delivered' THEN 1 ELSE 0 END) / count(*) AS share
FROM shipments;
-- 0
```

**Что происходит.** `sum` от целых даёт `bigint`, `count(*)` — тоже `bigint`. Деление целого на целое в Postgres — целочисленное: дробная часть отбрасывается. 246 000 / 300 000 = 0,82 → 0. Так же работает `int / int` в C#, так что сюрприз скорее в том, что в SQL об этом забываешь.

```sql
SELECT round(100.0 * sum(CASE WHEN status = 'delivered' THEN 1 ELSE 0 END) / count(*), 1)
       AS delivered_pct
FROM shipments;
-- около 82.0
```

**Что происходит.** `100.0` — литерал типа `numeric`. Умножение `numeric` на целое даёт `numeric`, дальше всё деление идёт в `numeric`. Порядок важен: `100.0 * a / b` считается слева направо, и `numeric` появляется до деления. Вариант `a / b * 100.0` даст 0, потому что целочисленное деление случится раньше.

### round() и float

```sql
SELECT round(random() * 100, 2);
-- ERROR:  function round(double precision, integer) does not exist
```

**Что происходит.** `random()` возвращает `double precision`. Функция `round` с числом знаков существует только для `numeric`: округлять двоичное число с плавающей точкой до двух десятичных знаков бессмысленно — результат всё равно нельзя точно хранить в `float`. Решение: `round((random() * 100)::numeric, 2)`. В учебной базе так сделано везде, где генерируются деньги и веса — загляни в скрипт. Почему для денег `numeric`, а не `float`, разбирали в [[1.3-Типы данных, которые реально нужны|уроке 1.3]].

### Текст, который выглядит как число

`shipments.meta` — `jsonb`. Оператор `->>` достаёт значение поля как текст:

```sql
SELECT id, meta->>'pallets' AS pallets
FROM shipments
WHERE meta->>'pallets' > '5'
LIMIT 10;
```

**Что происходит.** В результате будут перевозки с 6, 7, 8, 9 паллетами. С 10, 11, 12 и до 20 — не будет. Сравнивается текст с текстом, по алфавиту: `'10'` меньше `'5'`, потому что символ `'1'` идёт раньше `'5'`. Числа, хранящиеся как текст, сравниваются как слова.

Исправление — привести к числу. И тут вторая ловушка:

```sql
WHERE meta->>'pallets'::integer > 5
-- ERROR:  invalid input syntax for type integer: "pallets"
```

**Что происходит.** `::` связывается сильнее, чем `->>`. Postgres прочитал это как `meta ->> ('pallets'::integer)` и попытался превратить строку `'pallets'` в число. Нужны скобки:

```sql
SELECT id, (meta->>'pallets')::integer AS pallets
FROM shipments
WHERE (meta->>'pallets')::integer > 5
LIMIT 10;
```

**Что происходит.** Скобки заставляют сначала достать значение и только потом привести его к числу, поэтому 10 и 12 теперь больше 5. Это общий принцип: если сомневаешься в приоритете `::`, ставь скобки. Подробно про `jsonb` — в главе 14.3.

## LIKE и ILIKE: поиск по шаблону

`LIKE` сравнивает строку с шаблоном. В шаблоне два специальных символа:

|Символ|Значит|Пример|Совпадёт с|
|---|---|---|---|
|`%`|любая последовательность символов, в том числе пустая|`'Nord%'`|`Nord`, `Nord Steel AG`|
|`_`|ровно один любой символ|`'B-A_ 0%'`|`B-AB 0012`, `B-AZ 0450`|

```sql
SELECT id, name
FROM customers
WHERE name LIKE '%Logistics%'
LIMIT 10;
```

**Что происходит.** Postgres проверяет каждую строку: есть ли где-то внутри `Logistics`. `LIKE` чувствителен к регистру: `'%logistics%'` ничего не найдёт, потому что в данных слово с заглавной.

`ILIKE` — то же без учёта регистра. Это расширение Postgres, в стандарте его нет:

```sql
SELECT id, name
FROM customers
WHERE name ILIKE '%logistics%'
LIMIT 10;
```

**Что происходит.** Находятся те же строки, что с `'%Logistics%'`, в каком бы регистре ни был шаблон.

Несколько правил, которые надо знать:

- **Шаблон покрывает всю строку.** `name LIKE 'Nord'` найдёт только строки, равные `Nord`. Нужна подстрока — ставь `%` по краям.
- **NULL.** `NULL LIKE '%x%'` даёт `NULL`. `email NOT LIKE '%.example'` не вернёт клиентов без email — та же история, что с `<>` в [[2.2-NULL и трёхзначная логика|2.2]].
- **Экранирование.** Если надо найти сам символ `%` или `_`, перед ним ставится обратный слэш: `'скидка 50%' LIKE '%50\%%'` — `TRUE`. Без слэша `%` после `50` значил бы «что угодно».

### Почему `'%x'` медленнее, чем `'x%'`

Тут нужен взгляд вперёд, в главу 9. Обычный индекс B-tree хранит значения отсортированными — как словарь. Посмотри, как выглядят совпадения в отсортированном списке:

![[2.4-like-prefix-suffix.png]]
*Рис. 2.4.3. Шаблон с известным началом — это диапазон в отсортированном списке. Шаблон с % в начале — нет, его можно проверить только перебором.*

`LIKE 'nord%'` — это все строки от `nord` до `nore`. Они лежат подряд, и по индексу можно сразу прыгнуть к началу отрезка. `LIKE '%foods'` — совпадения разбросаны по всему списку, сортировка по началу строки ничем не помогает. Postgres прочитает все строки и проверит каждую.

Важная деталь, которая сработает против тебя в главе 9: даже `'nord%'` по обычному индексу работает не всегда — только при collation `"C"` или при специальном классе операторов индекса. Для поиска по подстроке есть отдельный инструмент — триграммный индекс (`pg_trgm` + GIN). Всё это в 9.6, 9.7 и 9.11. Сейчас запомни форму: `%` в начале шаблона — полный перебор.

## Регулярные выражения — кратко

Когда шаблона `LIKE` не хватает, есть регулярные выражения в стиле POSIX:

|Оператор|Значит|
|---|---|
|`~`|совпадает с регуляркой, с учётом регистра|
|`~*`|совпадает без учёта регистра|
|`!~`, `!~*`|не совпадает|

В отличие от `LIKE`, регулярка ищет совпадение _где угодно_ в строке. Нужно с начала — ставь `^`, до конца — `$`.

Проверка формата — найти налоговые номера, которые не похожи на «две буквы + девять цифр»:

```sql
SELECT id, vat_number
FROM customers
WHERE vat_number !~ '^[A-Z]{2}[0-9]{9}$';
```

**Что происходит.** Для каждого непустого `vat_number` Postgres проверяет шаблон. В учебной базе все номера сгенерированы правильно, поэтому строк не будет. Клиенты с `NULL` в результат тоже не попадут: `NULL !~ ...` даёт `NULL`. Такие проверки — первое, что пишут при разборе данных, загруженных из чужой системы.

Начало названия — один из нескольких вариантов:

```sql
SELECT id, name
FROM customers
WHERE name ~* '^(nord|baltic) ';
```

**Что происходит.** `~*` не учитывает регистр, `^` привязывает совпадение к началу строки, а пробел после скобки отсекает слова вроде `Nordic`.

Очистка строки — оставить в телефоне только цифры и плюс:

```sql
SELECT phone,
       regexp_replace(phone, '[^0-9+]', '', 'g') AS phone_clean
FROM drivers
WHERE phone IS NOT NULL
LIMIT 5;
```

**Что происходит.** `regexp_replace` заменяет все символы, кроме цифр и `+`, на пустую строку. Флаг `'g'` — «все вхождения», без него заменится только первое. Пробел после `+49` исчезнет.

Не всё надо делать регулярками. Достать домен из email проще функцией `split_part`:

```sql
SELECT split_part(email, '@', 2) AS domain, count(*) AS customers_cnt
FROM customers
WHERE email IS NOT NULL
GROUP BY domain
ORDER BY customers_cnt DESC
LIMIT 5;
```

**Что происходит.** `split_part` режет строку по `@` и берёт вторую часть. У нескольких клиентов совпадают имена компаний, поэтому домены повторяются. Регулярка тут сработала бы тоже, но `split_part` читается без расшифровки.

Есть ещё оператор `SIMILAR TO` — гибрид `LIKE` и регулярок из стандарта SQL. Он неудобный и внутри всё равно превращается в регулярку. Не используй.

## Как устроено: каталог приведений

Где Postgres берёт правила, что во что можно превращать и когда? Из системного каталога `pg_cast`. Каждая строка — одно разрешённое приведение «из типа A в тип B» с пометкой, когда его можно применять:

```sql
SELECT castsource::regtype, casttarget::regtype, castcontext
FROM pg_cast
WHERE castsource = 'integer'::regtype
  AND casttarget IN ('bigint'::regtype, 'numeric'::regtype, 'smallint'::regtype);
```

**Что происходит.** Увидишь три строки. `castcontext` — когда приведение разрешено:

|castcontext|Значит|Пример|
|---|---|---|
|`i`|неявно, в любом выражении|`integer` → `bigint`, `integer` → `numeric`|
|`a`|при присваивании: в `INSERT` и `UPDATE` в колонку этого типа|`integer` → `smallint`|
|`e`|только явно через `::` или `CAST`||

Отсюда поведение из урока. `customer_id = 17.0` работает, потому что `integer` → `numeric` помечено `i`, и Postgres сам вставляет приведение колонки. Обратное `numeric` → `integer` помечено `a`: при записи в колонку `integer` дробное значение округлится, а в сравнении само не применится. Приведения между текстом и большинством типов в `pg_cast` не лежат вовсе — их делают функции ввода-вывода типа, и только явно. Поэтому `'17'::text + 1` — ошибка.

Тип результата `CASE`, `COALESCE`, `UNION` выбирается по тем же правилам и до выполнения запроса: Postgres ищет тип, к которому неявно приводятся все ветки. Если такого нет — ошибка ещё на этапе разбора.

---

## Где ломается

**Порядок WHEN.** Широкое условие раньше узкого съедает узкую ветку. Ошибки нет, категория пропадает.

**Простой CASE с NULL.** `CASE x WHEN NULL` никогда не срабатывает. Только `CASE WHEN x IS NULL`.

**Типы веток CASE.** Число в одной ветке и текст в другой — ошибка. Приводи явно.

**Целочисленное деление.** `count / count` даёт 0. Нужен `numeric` до деления: `100.0 * a / b`.

**round от float.** `round(double precision, int)` не существует. Сначала `::numeric`.

**Числа в тексте.** `'10' < '5'` — сравнение по алфавиту. Приводи к числу.

**Приоритет `::`.** `meta->>'x'::int` приводит строку `'x'`, а не результат. Скобки.

**Приведение колонки вместо значения.** `col::text = '5'` или `int_col = 5.0` — работа в каждой строке и потеря индекса.

**LIKE чувствителен к регистру.** `'%logistics%'` не найдёт `Logistics`. Нужен `ILIKE`.

**`%` в начале шаблона.** Всегда перебор всех строк. Для поиска по подстроке нужен специальный индекс, глава 9.

> [!example] Мост в .NET
> **CASE.** Тернарный оператор в LINQ транслируется в `CASE`:
>
> ```csharp
> var rows = await db.Shipments
>     .Select(s => new
>     {
>         s.Id,
>         WeightClass = s.WeightKg >= 10000 ? "heavy"
>                     : s.WeightKg >= 1000  ? "medium"
>                     : "light"
>     })
>     .ToListAsync();
> ```
>
> **Что происходит.** Вложенные тернарные операторы становятся одним `CASE WHEN ... WHEN ... ELSE ... END`. `switch`-выражение C# транслируется так же. Порядок проверок сохраняется, значит и ловушка порядка — тоже.
>
> **Деление.** `(double)delivered / total` в LINQ переведётся в приведение к `double precision`. Для денег и процентов в отчётах лучше `decimal`: он станет `numeric`.
>
> **LIKE.** Npgsql даёт `EF.Functions.Like(name, "%Logistics%")` и `EF.Functions.ILike(name, "%logistics%")`. `name.Contains("x")` тоже транслируется: в EF Core 10 это `name LIKE '%x%'`, а значение из переменной уходит параметром с экранированными спецсимволами. Частая ошибка — `name.ToLower().Contains("x")`: в SQL получится `lower(name) LIKE ...`, функция над колонкой, без индекса. Для регистронезависимого поиска в Postgres — `ILike`.
>
> **Регулярки.** Npgsql переводит `Regex.IsMatch(s.Name, "^(Nord|Baltic) ")` в оператор `~`, а с `RegexOptions.IgnoreCase` — в `~*`. В начало шаблона он добавляет `(?p)`, чтобы переводы строк обрабатывались как в .NET.
>
> **Приведение колонки.** `s.CustomerId.ToString() == "17"` в LINQ даст `customer_id::text = '17'` — приведение колонки вместо значения, спрятанное в C#. Сравнивай с числом.

## Глубже / на синьора

**Ленивость CASE — не абсолютная.** Postgres вычисляет только выбранную ветку `CASE`, и на этом держится приём `CASE WHEN y <> 0 THEN x / y END`. Но есть исключение: константные подвыражения планировщик может вычислить заранее, до выполнения. `CASE WHEN x > 0 THEN 1/0 END` может упасть с делением на ноль, даже если ни одна строка не подходит. Агрегаты внутри `CASE` тоже вычисляются по всем строкам, независимо от ветки. Документация прямо об этом предупреждает. Для защиты от деления на ноль надёжнее `NULLIF` из [[2.2-NULL и трёхзначная логика|2.2]].

**`pg_input_is_valid`.** Безопасная проверка, можно ли привести строку к типу, без ошибки: `pg_input_is_valid('abc', 'integer')` → `false`. Удобно при разборе грязных данных: отфильтровать то, что не приводится, вместо падения всего запроса. Появилась в PostgreSQL 16.

**`citext`.** Расширение с регистронезависимым текстовым типом: `=` и `LIKE` на нём не различают регистр. Альтернатива `lower()` повсюду и `ILIKE`. Для email-адресов иногда используют. Сейчас чаще советуют недетерминированные collation, которые делают то же встроенными средствами.

**Регулярки и индексы.** `~ '^nord'` с якорем в начале теоретически тоже может использовать B-tree, как `LIKE 'nord%'`, с теми же оговорками про collation. Произвольные регулярки — только триграммный индекс.

**Где живёт приведение в плане.** В выводе `EXPLAIN` неявное приведение колонки видно: `Filter: ((customer_id)::numeric = 17.0)`. Если в фильтре над колонкой стоит `::` — это первый подозреваемый, когда индекс не используется. Вернёмся к этому в 9.7.

## На собесе

> [!question]- Как работает CASE и в каком порядке проверяются условия?
> **RU:** Условия проверяются сверху вниз, и первое, давшее TRUE, определяет результат — остальные не проверяются. FALSE и NULL одинаково ведут к следующему условию. Если ни одно не сработало и нет ELSE, результат NULL. Поэтому в цепочке диапазонов порядок — часть логики: широкое условие, поставленное раньше узкого, съест его ветку без всякой ошибки.
>
> **EN:** Conditions are checked top to bottom, and the first one that yields TRUE determines the result; the rest aren’t evaluated. FALSE and NULL both move on to the next condition. If nothing matches and there’s no ELSE, the result is NULL. That’s why order is part of the logic in range chains: a broad condition placed before a narrow one silently swallows its branch.

> [!question]- Почему `CASE x WHEN NULL THEN ...` никогда не срабатывает?
> **RU:** Простая форма CASE раскрывается в сравнение через `=`: `WHEN x = NULL`. Сравнение с NULL через `=` всегда даёт NULL, а не TRUE, поэтому ветка не выбирается никогда. Проверку на NULL можно сделать только в поисковой форме: `CASE WHEN x IS NULL THEN ...`.
>
> **EN:** The simple CASE form expands into equality: `WHEN x = NULL`. Comparing anything with NULL via `=` yields NULL, not TRUE, so that branch is never taken. You can only test for NULL in the searched form: `CASE WHEN x IS NULL THEN ...`.

> [!question]- Ты считаешь долю: `count_a / count_b` возвращает 0. Почему и как исправить?
> **RU:** Оба значения целые, а деление целого на целое в Postgres целочисленное — дробная часть отбрасывается. Нужно, чтобы хотя бы один операнд стал numeric до деления: `100.0 * a / b` или `a::numeric / b`. Порядок важен: в `a / b * 100.0` целочисленное деление уже случится. Потом округлить через `round(..., 2)` — он существует для numeric, но не для double precision.
>
> **EN:** Both values are integers, and integer division in Postgres truncates the fractional part. At least one operand must become numeric before the division: `100.0 * a / b` or `a::numeric / b`. Order matters: in `a / b * 100.0` the integer division has already happened. Then round with `round(..., 2)`, which exists for numeric but not for double precision.

> [!question]- Почему `LIKE '%abc'` не может использовать обычный индекс, а `LIKE 'abc%'` может?
> **RU:** B-tree хранит значения отсортированными по началу строки. Шаблон с известным началом — это непрерывный диапазон в этом порядке, и по индексу можно сразу перейти к его началу. Шаблон с `%` в начале ничего не говорит о первых символах, совпадения разбросаны по всему индексу, и остаётся перебрать все строки. Даже для `'abc%'` в Postgres нужен collation C или индекс с text_pattern_ops; для поиска по подстроке используют триграммный GIN-индекс из pg_trgm.
>
> **EN:** A B-tree keeps values sorted by their leading characters. A pattern with a known prefix is a contiguous range in that order, so the index can jump straight to its start. A leading `%` says nothing about the first characters, matches are scattered across the whole index, and the only option is to scan every row. Even `'abc%'` in Postgres needs the C collation or a text_pattern_ops index; substring search uses a trigram GIN index from pg_trgm.

> [!question]- Почему `WHERE int_column = 5.0` хуже, чем `WHERE int_column = 5`?
> **RU:** Литерал `5.0` имеет тип numeric, а оператора «integer равно numeric» нет. Postgres приводит колонку к numeric — в каждой строке. Индекс построен по integer и для условия по numeric не подходит, поэтому будет полный перебор. Общее правило: приводить значение к типу колонки, а не колонку к типу значения. В EXPLAIN это видно как `::numeric` над колонкой в Filter.
>
> **EN:** The literal `5.0` is numeric, and there’s no integer-equals-numeric operator. Postgres casts the column to numeric on every row. The index is built on integer and doesn’t match a numeric predicate, so you get a full scan. The rule is to cast the value to the column’s type, never the column to the value’s type. In EXPLAIN it shows up as `::numeric` on the column inside the Filter.
